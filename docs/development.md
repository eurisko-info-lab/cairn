# Development guide

This guide is for changing Cairn itself. Read [Core concepts](concepts.md) and
[Architecture](architecture.md) before making a cross-module change.

## Build commands

```bash
sbt -batch test
sbt -batch "tests/testOnly cairn.tests.LanguageStudioSuite"
sbt -batch examples/assembly
sbt -batch "examples/runMain cairn.examples.Main transcript transcripts/mvp.cairn"
sbt -batch "examples/runMain cairn.examples.Bench"
```

CI runs on JDK 17 and 21. It also checks the standalone jar, distribution smoke,
multi-host replica ceremony, golden digests, MVP/MAX transcripts, and language
source synchronization.

## Rust verifier (PR34 foundation)

The independent verifier lives in [verifier/README.md](../verifier/README.md).
Build and run it with Cargo:

```bash
cd verifier
cargo check
cargo run -- --help
```

Current commands verify federation certificate/proposal binding and replay
ledger-anchored federation transition history directly from on-disk `Node`
state (`chain` + `objects/`).

## Where code belongs

| Change | Primary location |
|---|---|
| Canonical artifact/checking primitive shared by both sides | `kernel/` |
| Pure language/change/Studio/migration logic | `content/core/` |
| Pack-specific definitions and workflows | `content/languages/`, `content/user/` |
| Proof/certification helpers | `content/proof/` |
| Effect request/response vocabulary | `contracts/` |
| CAS, filesystem, crypto, network, ledger I/O | `container/system-handler/` |
| Composition of content and handlers | `app/runtime/` |
| CLI, browser, transcript, LSP | `app/surface/` |
| Demonstrations and executable host wiring | `app/examples/` |
| Acceptance and regression coverage | `app/tests/` |

The enforced prohibition is `content/user ↛ container/system-handler`. Pure
Core proposes; Kernel checks; handlers perform authorized effects; Runtime
connects them.

## Common change recipes

### Add or change a language pack

1. Edit semantic data under `content/languages/<name>.cairn`.
2. Keep presentation in `<name>/surfaces/` where the pack uses split surfaces.
3. Add or update pack-loader, round-trip, composition, and behavioral tests.
4. Run `emit-languages` and inspect the diff.
5. Run the relevant suite and the full test suite.

Domain-specific changes, validations, migrations, and Studio commands should be
pack data interpreted by generic primitives. Do not add an operation-name
switch to a generic interpreter.

### Add a semantic change operation

Express it with `ChangeModel` primitives: parameters, queries, boolean checks,
mutations, access derivation, inverse, and surface syntax. Test apply, replay,
access traces, inversion, format preservation, and merge behavior.

### Add a Studio capability

Keep semantic commands in `StudioProfileSemantics` as ΔL elaborations. Keep
labels, layout, help, and widget hints in `StudioProfileSurface`. A language
without a profile must continue to work through grammar-derived forms.

### Add an external surface or projection

Record import provenance, validation, canonical semantic result, source
localization, migration behavior, and a round-trip or projection law. Do not
classify generated bytes as proof evidence.

### Add an optimization

Key it by semantic-model digest, interpreter-version digest, and input digest.
Retain a canonical interpreter path and test observational equivalence. The
system must remain correct when the cache is deleted.

## Canonical data and goldens

Canonical encoding is a compatibility boundary. If a change alters canonical
bytes, language digests, artifact kinds, or structural fingerprints:

1. determine whether the identity change is intended;
2. add migration or compatibility handling when stored artifacts require it;
3. run:

   ```bash
   sbt -batch "examples/runMain cairn.examples.Main digests"
   sbt -batch "examples/runMain cairn.examples.Main emit-languages"
   git diff -- app/tests/golden content/languages
   ```

Never accept a golden diff merely to make CI green.

## Test strategy

- Unit tests cover canonical codecs and local laws.
- Acceptance suites cross module boundaries.
- Transcripts cover user-visible end-to-end behavior.
- Property/fuzz suites exercise round trips, canonicalization, repository DAGs,
  and generated terms.
- Boundary suites inspect source dependencies and forbidden imports.
- Agreement suites keep external/native claims separate from kernel proof.

New behavior should normally have the narrowest useful unit law and one
end-to-end acceptance path.

## Documentation expectations

Update the newcomer path when a change alters how the project is understood or
run. Update architecture for module/trust changes, assumptions for deliberate
gaps, operations for CLI behavior, concepts for public semantic abstractions,
and the roadmap for status. Avoid repeating long reference material across
multiple files; link to its source of truth.
